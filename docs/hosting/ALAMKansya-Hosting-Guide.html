Hosting ALAMKansya for the judges

Option B: one small server on the DataWave AWS account, with its own permission to call Bedrock · Group Oreo Bread · 16 Nov 2026

What you are building

One Ubuntu server (EC2) in Singapore runs the same app we run on our laptops: the built-in database, the Python backend and the Next.js frontend. In front of it, Caddy adds HTTPS and a username and password for the judges. The server is given an IAM role that lets it call Bedrock, so nobody has to sign in to AWS every few hours.

Judge's browser ──HTTPS──▶ Caddy (ports 80/443, password)
                              │
                              ▼
                     Next.js frontend  127.0.0.1:10012
                              │  /api/*
                              ▼
                     FastAPI backend   127.0.0.1:8000
                        │                    │
                        ▼                    ▼
              Built-in Postgres     Amazon Bedrock (Claude + Cohere)
              (pgserver, on disk)   via the server's IAM role

Only Caddy is reachable from the internet. The frontend and backend listen on the server itself, as they do on our laptops.

Before you start

  • The latest code is on GitHub. The new features (alerts, gap map, review checks, follow-ups) are not committed yet. Commit and push to origin main first. Never commit backend/.env.local.
  • The AWS console, signed in to the DataWave account, region Asia Pacific (Singapore) ap-southeast-1.
  • Bedrock model access is already on for this account (the app already calls Claude Sonnet 5.5 and Cohere Embed v4 there).
  • About 2 hours.

1Create the IAM role for the server

  1. IAM → Roles → Create role → Trusted entity: AWS service, use case EC2.
  2. Attach AmazonSSMManagedInstanceCore (lets you open a terminal from the browser, so no SSH key is needed).
  3. Name it alamkansya-demo-role and create it.
  4. Open the role → Add permissions → Create inline policy → JSON, paste this, name it bedrock-invoke:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
    "Resource": "*"
  }]
}

"Resource": "*" is the simple choice for a short demo: the global. model IDs route across regions, so a narrow policy has to list the inference profile and the model in every region. Tighten it for anything longer-lived.

2Launch the server

  1. EC2 → Launch instance. Name: alamkansya-demo.
  2. Image: Ubuntu Server 24.04 LTS, architecture 64-bit (x86).
  3. Type: t3.medium. Key pair: optional (Session Manager works without one).
  4. Network: allow HTTP (80) and HTTPS (443) from anywhere. Leave SSH (22) off, or allow it from My IP only. Do not open 8000 or 10012.
  5. Storage: 20 GB gp3.
  6. Advanced details → IAM instance profile: alamkansya-demo-role.
  7. Launch. Then EC2 → Elastic IPs → Allocate → Associate it with the instance. Write the address down, e.g. 13.229.10.20.

Your site name will be the address with dashes plus .sslip.io, e.g. 13-229-10-20.sslip.io. It points at your Elastic IP with no DNS setup. (If the team owns a domain, add an A record to the Elastic IP and use that name instead.)

3Open a terminal on the server

EC2 → select the instance → Connect → Session Manager → Connect. Then switch to the normal user (the database refuses to run as root):

sudo -iu ubuntu

4Install the tools

# System packages: Python 3.12 (Ubuntu 24.04's default), git, build tools
sudo apt-get update
sudo apt-get install -y python3.12-venv python3-pip git build-essential curl

# Node.js 22
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt-get install -y nodejs

# Caddy (HTTPS + password)
sudo apt-get install -y debian-keyring debian-archive-keyring apt-transport-https
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt-get update && sudo apt-get install -y caddy

# Only on t3.small: add 2 GB of swap for the frontend build
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

5Get the code

The repo is private, so give the server a read-only deploy key:

ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519
cat ~/.ssh/id_ed25519.pub

On GitHub: repo → Settings → Deploy keys → Add key → paste it (leave “write access” off). Then:

git clone git@github.com:mcfcs/bpi.git ~/bpi
cd ~/bpi

6Set up the backend

cd ~/bpi/backend
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt

# Check the server can reach Bedrock with its role (should print the account number)
.venv/bin/python -c "import boto3; print(boto3.client('sts').get_caller_identity()['Account'])"

Create the settings file. Do not add AWS_PROFILE: without it, the app uses the server’s IAM role.

cat > ~/bpi/backend/.env.local <<'EOF'
LLM_PROVIDER=bedrock
AWS_REGION=ap-southeast-1
AWS_BEDROCK_MODEL=global.anthropic.claude-sonnet-5-5
LLM_EFFORT=medium
EMBEDDING_PROVIDER=bedrock
EMBEDDING_MODEL=global.cohere.embed-v4:0
EOF

# First run: starts the built-in database, applies migrations, seeds the synthetic studies,
# embeds the findings with Bedrock, and adds DATABASE_URL and DEMO_MODE to .env.local.
.venv/bin/python scripts/dev_db.py

It should end with “Seeded 33 approved studies; 6 new report(s) in the review queue” and “Embedded 160 findings with bedrock:global.cohere.embed-v4:0”. Then stop it; the service in step 8 starts it again:

.venv/bin/python scripts/dev_db.py --stop

7Build the frontend

cd ~/bpi/frontend
npm ci
BACKEND_URL=http://127.0.0.1:8000 npx next build

8Run both as services (start on boot, restart on failure)

sudo tee /etc/systemd/system/alamkansya-api.service >/dev/null <<'EOF'
[Unit]
Description=ALAMKansya backend and database
After=network-online.target
Wants=network-online.target

[Service]
User=ubuntu
WorkingDirectory=/home/ubuntu/bpi/backend
# Starts or reuses the built-in database, migrates and seeds if empty
ExecStartPre=/home/ubuntu/bpi/backend/.venv/bin/python scripts/dev_db.py
ExecStart=/home/ubuntu/bpi/backend/.venv/bin/python -m uvicorn app.main:create_app --factory --host 127.0.0.1 --port 8000
Restart=on-failure
TimeoutStartSec=600

[Install]
WantedBy=multi-user.target
EOF

sudo tee /etc/systemd/system/alamkansya-web.service >/dev/null <<'EOF'
[Unit]
Description=ALAMKansya frontend
After=alamkansya-api.service
Wants=alamkansya-api.service

[Service]
User=ubuntu
WorkingDirectory=/home/ubuntu/bpi/frontend
Environment=NODE_ENV=production
Environment=BACKEND_URL=http://127.0.0.1:8000
ExecStart=/usr/bin/npx next start -H 127.0.0.1 -p 10012
Restart=on-failure

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now alamkansya-api alamkansya-web

# Check: llm_ready and search_ready should both be true
curl -s http://127.0.0.1:10012/api/health

9Add HTTPS and the judges’ password

# Make a password hash (type the password when asked)
caddy hash-password

sudo tee /etc/caddy/Caddyfile >/dev/null <<'EOF'
13-229-10-20.sslip.io {
    basic_auth {
        judges PASTE_THE_HASH_HERE
    }
    reverse_proxy 127.0.0.1:10012
}
EOF

sudo systemctl reload caddy

Use your own sslip.io name. Within a minute Caddy gets a certificate. Open https://13-229-10-20.sslip.io: the browser asks for the username judges and the password, then the app opens.

Why a password: the demo sign-in lets anyone pick Ben or Ana without a password, which is what we want for judges, but anyone with the link could otherwise use up Bedrock credit. If Caddy prints an error about basic_auth, your Caddy is older: write basicauth instead.

10Reset the demo every night

Approving the Mindanao report uses up the demo, so the next judge would find it already done. This script puts everything back:

cat > ~/reset-demo.sh <<'EOF'
#!/bin/bash
set -euo pipefail
cd /home/ubuntu/bpi/backend
sudo systemctl stop alamkansya-web alamkansya-api
.venv/bin/python scripts/dev_db.py --reset
.venv/bin/python scripts/dev_db.py --stop
sudo systemctl start alamkansya-api alamkansya-web
EOF
chmod +x ~/reset-demo.sh

# Every day at 03:00 Manila time (19:00 UTC)
(crontab -l 2>/dev/null; echo "0 19 * * * /home/ubuntu/reset-demo.sh >> /home/ubuntu/reset.log 2>&1") | crontab -

Run ~/reset-demo.sh by hand any time, e.g. after a rehearsal.

Updating the server after a change

cd ~/bpi && git pull
cd backend && .venv/bin/pip install -r requirements.txt
cd ../frontend && npm ci && BACKEND_URL=http://127.0.0.1:8000 npx next build
sudo systemctl restart alamkansya-api alamkansya-web

New database migrations apply on restart.

Tearing it down after judging

  1. EC2 → Instances → alamkansya-demo → Terminate (this deletes the disk and its synthetic data).
  2. EC2 → Elastic IPs → Release the address (it costs money while unattached).
  3. IAM → delete alamkansya-demo-role. GitHub → remove the deploy key.
  4. Delete the budget if you no longer need it.
